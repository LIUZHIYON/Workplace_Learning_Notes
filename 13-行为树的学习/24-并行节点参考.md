# Parallel Nodes 逐段解释

> 来源：https://behaviortree.dev/docs/nodes-library/ParallelNode
> 说明：这是 Nodes Library（节点库）系列的一篇，系统讲解 **Parallel（并行节点）** 的用法，包括 Parallel 和 ParallelAll 两种变体。

---

## 一、核心概念

**原文大意：**
> Parallel 节点会**并发**执行所有子节点，但**不是在独立线程里**。所有子节点在单次 tick 中顺序执行，多个子节点可能同时处于 RUNNING 状态。

> ⚠️ "Parallel" 指的是多个子节点可以同时 **RUNNING**。子节点仍然在同一个线程里顺序 tick。要实现真正多线程执行，子节点内部必须实现异步节点。

**我的解释：**

```
Sequence 的行为：
  tick 1: A → SUCCESS ✅ → B → FAILURE ❌ → C 根本不会被执行

Parallel 的行为：
  tick 1: A → RUNNING 🔄, B → SUCCESS ✅, C → RUNNING 🔄
  tick 2: A → SUCCESS ✅, C → FAILURE ❌
  多个子节点各自的 RUNNING/SUCCESS/FAILURE 彼此独立
```

**Parallel 是唯一可以同时有多个子节点处于 RUNNING 状态的控制节点。**

## 二、Parallel（标准并行节点）

### 端口参数

| 端口 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `success_count` | InputPort\<int\> | -1 | 返回 SUCCESS 所需的子节点成功数 |
| `failure_count` | InputPort\<int\> | 1 | 返回 FAILURE 所需的子节点失败数 |

**负数索引（Python 风格）：**
> `-1` 表示"子节点总数"。比如有 4 个子节点时，`success_count="-1"` 意味着全部 4 个都要成功。

**默认行为：**
> success_count=-1（全部成功），failure_count=1（一个失败就不行）→ 相当于 **"只要有一个失败就失败，全部成功才算成功"**

### XML 示例

```xml
<Parallel success_count="2" failure_count="2">
    <ActionA/>
    <ActionB/>
    <ActionC/>
</Parallel>
```

**3 个子节点时的行为：**

```
如果先有 2 个成功（达到 success_count=2）→ Parallel 返回 SUCCESS ✅
                                  → 停下还在 RUNNING 的子节点
如果先有 2 个失败（达到 failure_count=2）→ Parallel 返回 FAILURE ❌
                                  → 停下还在 RUNNING 的子节点
```

**示意图：**

```
场景：ActionA 快速成功，ActionB 快速失败，ActionC 还在跑

tick 1: ActionA → SUCCESS ✅（1/2 成功）
        ActionB → FAILURE ❌（1/2 失败）
        ActionC → RUNNING 🔄
  还没达到任一阈值 → 继续 RUNNING

tick 2: ActionA → SUCCESS ✅（仍 1/2 成功）
        ActionB → FAILURE ❌（仍 1/2 失败）
        ActionC → RUNNING 🔄（仍在跑）

tick 3: ActionC → FAILURE ❌ → 2/2 失败达到阈值
        → Parallel 返回 FAILURE ❌
        → ActionA 被 halt（但已经完成了）
```

## 三、ParallelAll（全部完成并行节点）

### 端口参数

| 端口 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| `max_failures` | InputPort\<int\> | 1 | 允许的最大失败数 |

### 行为规则

- 返回 **SUCCESS**：如果失败数 **小于** `max_failures`
- 返回 **FAILURE**：如果失败数 **等于或大于** `max_failures`
- **跟 Parallel 的关键区别：不会提前 halt 子节点**，所有子节点都会跑到完成

### XML 示例

```xml
<ParallelAll max_failures="2">
    <ActionA/>
    <ActionB/>
    <ActionC/>
</ParallelAll>
```

**示例行为：**

```
情况 1：ActionA FAILURE, ActionB SUCCESS, ActionC SUCCESS
  → 失败数=1 < max_failures=2 → SUCCESS ✅

情况 2：ActionA FAILURE, ActionB FAILURE, ActionC SUCCESS
  → 失败数=2 >= max_failures=2 → FAILURE ❌

情况 3：max_failures="-1"
  → 永远返回 SUCCESS（因为失败数不可能 >= 子节点数）
```

## 四、Parallel vs ParallelAll 对比

| 特性 | Parallel | ParallelAll |
|---|---|---|
| **提前终止** | ✅ 达到阈值就 halt 还没完的子节点 | ❌ 所有子节点都会跑到完成 |
| **成功阈值** | 可配置 `success_count` | 所有未失败的子节点 |
| **失败阈值** | 可配置 `failure_count` | 可配置 `max_failures` |
| **适用场景** | 竞赛条件（谁先到达阈值） | 必须全部尝试执行完 |

**我的解释：**

```
用 Parallel 的场景：
  "去三个商店买水，任何一家买到就回来"
  不需要所有商店都跑完，有一个成功就够了。

用 ParallelAll 的场景：
  "尝试三个恢复策略——转一圈、后退、重置路径"
  每个策略都需要执行完，不能中途打断，因为要看到副作用结果。
```

## 五、实际项目中的常见用法

### 用法 1：N-of-M 成功

```xml
<!-- 5 个传感器，至少 3 个验证通过才算通过 -->
<Parallel success_count="3" failure_count="3">
    <SensorCheck1/>
    <SensorCheck2/>
    <SensorCheck3/>
    <SensorCheck4/>
    <SensorCheck5/>
</Parallel>
```

### 用法 2：全部执行完但容错

```xml
<!-- 存盘前保存多个日志，允许 1 个失败 -->
<ParallelAll max_failures="1">
    <SaveToDisk/>
    <UploadToCloud/>
    <SendNotification/>
</ParallelAll>
```

## 六、跟 Sequence / Fallback 的对比总结

| 节点类型 | 子节点同时 RUNNING？ | 成功条件 | 失败条件 |
|---|---|---|---|
| **Sequence** | ❌ | 全部成功 | 一个失败就停 |
| **Fallback** | ❌ | 一个成功就停 | 全部失败 |
| **Parallel** | ✅ | 配置 `success_count` | 配置 `failure_count` |
| **ParallelAll** | ✅ | 失败数 < `max_failures` | 失败数 >= `max_failures` |

**一句话总结：**
> `Parallel` 让多个子节点同时跑（都不阻塞），谁先达到阈值就决定结果并放弃其他。`ParallelAll` 要求所有子节点都跑完才决定结果。两者都是单线程的"并发"不是多线程。
